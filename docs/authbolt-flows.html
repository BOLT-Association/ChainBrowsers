AuthBOLT sign-in

A person signs up for a site without a password. Their wallet holds an identity token they issued themselves, and shows it to the site when they approve. The site checks the proof against the chain and remembers the token's issuer key as the account.

no passwords one key per identity presentations are never broadcast verified live 2026-10-07, regtest
The model

Users issue, apps verify

An AuthBOLT is a BOLT token (b017) of type AuthBOLT. The person mints it with their own wallet, so the person is the issuer. A site never sees a list of trusted issuers. It learns the issuer key when the person registers and recognises it from then on.

Each new identity gets a new key. A person can use one identity everywhere or mint one per site, and two sites cannot link identities that use different keys. The token moves only to the person's own keys: the holder key can rotate, but the issuer key never changes, so it is the account's identity at the site.

To prove they hold the identity, the wallet makes a presentation: an unfunded commit and settle transaction that carries up to 75 bytes of data. It is a self-transfer: the token goes back to the person's own key. The site's app key travels inside the auth data, which the presentation signs over. Nobody broadcasts it. The site's server checks it and throws it away.

Who takes part

Four parties, one prompt

The page

PeerLoop in a Hodos tab. It asks for a presentation through window.BOLT, which Hodos injects into external https pages only. It cannot mint or present.

Hodos

The browser shell holds the page's request and opens Hodos's own prompt. The Rust wallet derives the identity keys and signs. The person decides here.

App server

PeerLoop's p2pd. It issues single-use challenges, keeps accounts keyed by issuer key, and runs short sessions.

Verifier and chain

The bolt-verify sidecar runs b017's verifier. It asks Arcade only whether an anchor was seen, and asks p2pd's own verified header chain whether a merkle root is real.

What a presentation carries

66 bytes of auth data

The server builds the data. The page passes it on unchanged. The wallet reads the first two fields to word its prompt, and refuses data that names a different app from the one asking.

What reaches the chain

Three kinds of transaction

A presentation package is [anchor, commit, settle]. The anchor is the token transaction the package stands on: the mint for an identity that has never moved, or the last settle that went on chain after a rotation.

TransactionWho broadcasts itWhat it does
MintThe wallet, once, when the person creates the identityCreates the 1-sat AuthBOLT under a fresh key. Funded.
Anchor resendThe verifier, on every checkSends the anchor to Arcade again. Arcade answers “already seen”, which shows the token's history is real. A resend changes nothing. A mined anchor whose merkle path matches p2pd's header chain is not resent.
Commit and settleNobodyThe presentation itself: a self-transfer back to the holder's own key, carrying the 66 bytes. It is unfunded and creates value, so no node would accept it. The verifier runs its scripts off chain and throws it away. The token stays with the person.
RotationThe wallet, when the person rotatesA self-transfer to a new holder key: a funded commit and settle, both broadcast. The issuer key does not change. This is a separate action, not part of signing in.
Flow 1 · tag 0x01

Registration

The person fills in a username and, optionally, an email, X handle or LinkedIn profile. The form is hashed into the challenge, so the proof covers exactly what they submitted.

The optional links are only what the identity's holder chose to submit. Proving them needs its own step: an email link, or OAuth or a posted code for X and LinkedIn.

Flow 2 · tag 0x02

Sign in

The same exchange without the form. The server accepts a presentation whose issuer key matches an account, whatever holder key the token has now.

Flow 3 · tag 0x03

Keep-alive

A session lasts 30 minutes. While the person stays on the site, the page renews it every 10 minutes with a fresh presentation. If the person ticked "Keep me signed in", Hodos answers without showing anything.

When the wallet would have to ask, it answers NEEDS_PROMPT instead of opening a window. The page stops its keep-alives and the session ends at its expiry. Nothing waits on the person. A network error is different: the page tries again at the next tick.

Why the site can trust it

What gets checked

The verifier, on every presentation

  • The package holds an AuthBOLT, and b017 verifies it with the issuer key the token names.
  • The token's anchor was seen by the network (Arcade), and every merkle root is in p2pd's own verified header chain.
  • It is a presentation, not a mint or a transfer.
  • Its data equals this challenge's 66 bytes exactly.
  • The data names this site's app key, so the package cannot be replayed to another site.
  • It is a self-transfer: the settle pays the same key the commit spent from. A package that moves the token to anyone else is refused.

The app server, before it acts

  • The challenge exists, has not expired (2 minutes) and was not used. It is consumed on first use, whatever the verdict.
  • The verified purpose matches the route: register, sign in or refresh.
  • Registration: no other account has this issuer key.
  • Keep-alive: the challenge was asked for by this session, and the issuer key is this account's.

Nobody takes a server's word about the chain. Hodos runs in spv mode and keeps only headers that pass its own checks. p2pd does the same with the same rules: layout, proof of work, linkage, pinned genesis, most work wins. Both take candidate headers from Arcade's chaintracks and wake on its tip stream.

What a site cannot do

The person stays in control

  • Mint or present. A page can only request a presentation. Minting and presenting happen in Hodos's own prompt, which the page cannot script.
  • See other identities. BOLT.list() returns only identities already linked to this site and app. A site cannot write to an identity record.
  • Use the identity keys. The wallet refuses the keys' protocol, authbolt identity, to every site, for signing and for getPublicKey.
  • Claim to be another site. Hodos stamps the requesting domain itself. The page's word is not used.
  • Answer the prompt. Only Hodos's approval overlay may send the answer. A tab that navigates to the prompt page is refused.
  • Keep a session alive unasked. A silent presentation needs the person's earlier "Keep me signed in" for that app on that site, and only ever carries keep-alive data.

Open items

  • An Identities list in the Hodos wallet panel, to see, unlink and rotate identities and withdraw "Keep me signed in".
  • Linking identities to each other, on or off chain.
  • Mainnet header rules. Both header chains follow regtest rules only.
  • An old holder key can still present after a rotation, because the check is that the anchor was seen, not that it is unspent. Every old holder key is the person's own, so this matters only if one leaks.
  • BSV Browser support is set aside for now.
